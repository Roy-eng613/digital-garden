# WEB小説におけるアジャイル開発手法の適用

WEB小説の連載は、構造だけ見ればアジャイル開発に似ている。短い単位で出し、反応を見て次を変える。実際にどこまで持ち込めるのか、自分の制作に引き寄せて整理する。

## 対応させる

| 開発 | 小説 |
| :--- | :--- |
| イテレーション | 1話（または週次の更新単位） |
| プロダクトバックログ | 設定ノート、未回収の伏線、書きたいシーン |
| レビュー | 読者コメント、PV、読了率 |
| レトロスペクティブ | 公開後の振り返り（何が読まれ、何が飛ばされたか） |
| 継続的インテグレーション | 公開前の整合性チェック |

## 持ち込める部分

- **小さく出す**：書き溜めてから出すより、反応が早く返る。
- **状態を外に出す**：設定をノートに分けるほど、続きを書くコストが下がる。
- **検査を自動化する**：矛盾チェックは機械的にできる。

## 持ち込んではいけない部分

読者を開発チームの一員として扱うこと。アジャイルでは顧客がバックログに参加するが、小説でそれをやると、声の大きい読者の好みに最適化される。**読者はレビュアーであって、共同作者ではない**。

もうひとつ、スプリントの速度を上げると、作品の密度が落ちる。週次で出すために、説明で埋める。これはAIが一番やりたがる省略でもある。

## 使いどころ

アジャイルが効くのは、整合性の管理と公開のリズム。効かないのは、何を書くかの決定。そこは最後まで作者が持つしかない。
